# Design: panels

Issue: #44. Builds on: layout (#41), [elements](element.md) (#42), [layout tests](layout-tests.md) (#56), `XamlEnum` (#19), [golden images](golden-images.md) (#38). Unblocks: `Grid` (#67), `DockPanel` (#68), `WrapPanel` and `UniformGrid` (#69), `Canvas` (#70), the accesskit adapter (#54), #49.

`StackPanel` is the first layout container: it holds children and lines them up in a row or a column, with a background drawn under them. Building it the way the rest of the panels will be built needs a few changes underneath first: how `#[element]` and `#[derive(XamlType)]` share work, where a type's XAML content is declared, what the property groups are called, how layout treats `Collapsed`, and where children live.

```rust
#[element]
#[xaml(namespace = "https://artic.rs/ui")]
pub struct StackPanel {
  #[xaml(flatten)] pub panel: Panel,
  #[xaml(content)] pub children: Children,
  #[xaml(affects = layout)] pub orientation: Property<Orientation>,
  #[xaml(affects = layout)] pub spacing: Property<f32>,
}

impl ElementImpl for StackPanel {
  fn measure_override(&self, cx: &mut MeasureCx<'_>, available: Size) -> Size { /* section 5 */ }
  fn arrange_override(&self, cx: &mut ArrangeCx<'_>, size: Size) { /* section 5 */ }
  fn render(&self, cx: &mut RenderCx<'_>, scene: &mut SceneBuilder) {
    self.panel.render(cx, scene);
  }
}
```

Shared behavior is composed explicitly. A property group holds data and methods, and a control calls the methods it uses from its `ElementImpl` hooks. Nothing runs because a field's type says so, so a control's hooks show everything it does. Groups that hook into the element by themselves were considered and rejected: they behave like base classes, their hooks need an order, and the four built-in groups depend on each other's fields (`hit_test` reads `visibility`), which would turn into coupling between hooks.

## 1. Building controls

### `#[element]` and `#[derive(XamlType)]`

`#[element]` adds `#[derive(XamlType)]` to the struct it rewrites, instead of calling the derive's functions itself. It keeps the work that makes a struct an element: it rejects generic and tuple structs, a written `derive(XamlType)` or `derive(Default)` and the reserved field names; adds the four group fields; implements `HasState` for `#[element(state)]` fields; and writes `Layoutable`, `Element` and `element_type!`. It strips only its own `#[element(...)]` attributes and leaves `#[xaml(...)]` to the derive.

### Overriding defaults

A property's default is set where it's declared, with `#[xaml(default = value)]`. A type that changes the default of a property it doesn't declare, one from a flattened group, says so with a flag on the struct and implements `OverrideDefaults`, a trait in `artic-registry`:

```rust
#[element]
#[xaml(namespace = "https://artic.rs/ui", override_defaults)]
pub struct Button { /* … */ }

impl OverrideDefaults for Button {
  fn override_defaults(&self) {
    self.interaction.focusable.set_default(true);
    self.interaction.cursor.set_default(Cursor::Hand);
  }
}
```

With the flag, the derive's `Default` builds every field and then calls `<Self as OverrideDefaults>::override_defaults(&value)`; without it, `Default` builds the fields and stops. The flag is needed because a derive sees only its struct, never an `impl` block, so the struct has to say that the impl exists. The flag is named after its trait so the one leads to the other, and isn't called `defaults`, which would sit one letter from the field-level `default = …` and read like serde's `#[serde(default)]`.

Elements use the same flag and trait as any other type, so `ElementImpl::defaults` is removed and `#[element]` has nothing to do with defaults. A struct-level list, `#[xaml(default(interaction.focusable = true, …))]`, was considered and rejected: a control that changes several defaults would carry a long attribute.

### Content on the field

The member that receives a type's XAML content is marked where it's declared, with `#[xaml(content)]`, and the struct-level `#[xaml(content = name)]` is removed, so renaming it can't leave a stale name behind. Content comes in two kinds, and `TypeInfo.content` says which, taking the place of the [loader design](loader-values.md)'s separate `TypeInfo.add_child`:

```rust
pub enum ContentInfo {
  /// A property that takes the content as its value, such as `ContentState`'s
  /// `Property<Content>`, which accepts text, an element or data (#84). The loader sets it
  /// through the property's `PropertyAccess`, as for any property.
  Property(PropertyRef),
  /// A collection field that takes child elements: `Children` or `Child`, which link them into
  /// the tree (section 4), or a value collection such as `Vec<GradientStop>`, which takes each
  /// staged value out of the tree into the field.
  /// `add_child` is generated by the derive: it calls the field's `XamlCollection::push_child`
  /// with an accessor to the field built in.
  Collection {
    field: &'static str,
    add_child: fn(&mut UiTree, NodeId, NodeId) -> Result<(), ValueError>,
  },
}
```

A property may be marked in a property group, as `ContentState.content` is: the group's derive exposes `const CONTENT: Option<&'static str>`, and the outer derive builds the `PropertyRef` with the group's field, the way `PropertyRef` already names group properties. A `Children` or `Child` field is declared on the type itself, as every panel's `children` is (section 5); a group holds properties and the methods that use them. A type has at most one content member, counting its groups: the derive checks its own fields, and a `const` assertion over its groups' `CONTENT` checks the rest. A single child is a `Child` field, not a `Property<Option<NodeId>>`, so the tree link has no second copy; content that may be text or data stays a property, since it isn't always a node.

### Group names

The property groups are renamed after their fields: `LayoutProperties` becomes `Layout`, `AppearanceProperties` `Appearance`, `InteractionProperties` `Interaction` and `IdentityProperties` `Identity`. Each group holds methods as well as properties (`Layout::measure`, `Interaction::hit_test`), so the suffix described only half of them, and `field: Type` now reads the same everywhere: `layout: Layout`, `panel: Panel`. The derive keeps its name, `XamlProperties`, since properties are what it generates. The test-local `Panel` structs in `artic-platform/tests/common/mod.rs` and the `artic-core` tree docs are renamed so that `Panel` names one thing.

## 2. Enums in `artic-layout`

`#[derive(XamlEnum)]` generates a `FromStr` whose error is `ParseEnumError`, which lives in `artic-core`. The derive names it through the first of its candidate crates the calling crate depends on. `XamlEnum` gets a candidate list of its own, `artic`, `artic-registry`, then, new here, `artic-core`, whose `__private` module re-exports `ParseEnumError`; `XamlType` keeps its list without `artic-core`, since its output needs the registry's descriptors. Until now the candidates stopped at `artic-registry`, which is why `artic-layout`, depending only on `artic-core`, parsed its two alignments by hand.

`artic-layout` depends on `artic-macros` and derives the parser for `HorizontalAlignment`, `VerticalAlignment` and `Orientation`; the hand-written parsers are deleted:

```rust
/// The axis a panel stacks or wraps its children along.
#[derive(Debug, Clone, Copy, Default, Eq, PartialEq, Hash, XamlEnum)]
pub enum Orientation {
  Horizontal,
  #[default]
  Vertical,
}
```

`Orientation` sits in `sizing.rs` beside the alignments, where a contributor looks for layout vocabulary. The new edge makes no cycle: `artic-macros` depends on no artic crate, and its output names crates the caller already depends on. A proc macro runs on the build machine, so the web target gains nothing.

## 3. Collapsed children

A `Collapsed` element takes no part in layout. Today it measures to zero, so a panel can't tell it from a visible element that is empty, and `StackPanel` would put spacing around it. `artic-layout` learns the idea without naming `Visibility`:

```rust
pub trait Layoutable {
  fn measure(&self, cx: &mut MeasureCx<'_>, available: Size) -> Size;
  fn arrange(&self, cx: &mut ArrangeCx<'_>, rect: Rect);
  /// Whether the node takes no part in layout. By default, false.
  fn collapsed(&self) -> bool {
    false
  }
}
```

`#[element]` implements it from `appearance.visibility`. The manager leaves collapsed children out of `MeasureCx::children()` and `ArrangeCx::children()`, and so out of `measure_children` and `arrange_children`, so no panel writes code for them. A container that names a collapsed child directly gets the same answer: `MeasureCx::measure` returns zero without measuring it and `ArrangeCx::arrange` does nothing, so no path leaves it with a size or rectangle. Its subtree is covered by the rule `element.md` already gives the manager: children a measure didn't measure are forgotten with their subtrees, and the dirty and waiting passes skip forgotten nodes, so a descendant invalidated while its ancestor stays collapsed isn't measured either. A collapsed node keeps no results: `desired` and `rect` return `None`, as for a child a measure skipped. A collapsed root lays out nothing.

Collapsing a child used to reach its parent as a desired size that changed to zero. Now the child isn't measured, so the manager watches membership instead: when a dirty node's `collapsed()` answer differs from the last pass, its parent's measure is marked dirty, the same path a removed child takes. `Layout::measure` and `Layout::arrange` lose their `Collapsed` branch, since the manager no longer calls them for a collapsed node; `Hidden` is measured and arranged as before.

The walks that follow layout skip a node it didn't lay out, with its subtree. Composition already skips a node and its subtree when `Nodes::layers` returns `visible: false` (`Compositor::visit`), so `ElementNodes::layers` returns that for a node with no layout rectangle, instead of drawing it at `Rect::ZERO`; hit testing follows the same rule, and #54's accesskit walk will too. `element.md`'s `Collapsed` row becomes: not laid out, no rectangle, skipped by drawing, hit testing and accessibility.

Layout arithmetic gets one rule for overflow, in place of fixes at each place a sum can grow: the geometry operations layout uses saturate at the finite range. `Rect::snap`, which scales edges and subtracts them, `Rect::deflate` and `inflate`, which add margins, and `Size` sums return `f32::MAX` or `f32::MIN` (that is, `-f32::MAX`) by sign instead of an infinity, so finite inputs always give finite rectangles. That keeps the manager's rule, a finite desired size and rectangle, true however large the values a panel adds up, without each panel guarding every addition.

## 4. Children

The tree owns a panel's children; a panel keeps no list of its own. Two copies of "who are my children" would drift, and a method on the panel couldn't update both, since the panel lives inside the tree it would have to borrow. `Children` is an empty type that marks the content field, in `artic-element`:

```rust
/// Marks an element's XAML children: they become its logical and visual children.
#[derive(Debug, Default, Clone, Copy)]
pub struct Children;

impl Children {
  pub fn add(tree: &mut UiTree, parent: NodeId, child: NodeId);
  pub fn insert(tree: &mut UiTree, parent: NodeId, index: usize, child: NodeId);
  /// Detaches `child` from `parent` in both trees; the node stays allocated.
  pub fn remove(tree: &mut UiTree, parent: NodeId, child: NodeId);
}
```

A single child works the same way, as a collection of at most one:

```rust
/// Marks an element's single XAML child: its only logical and visual child.
#[derive(Debug, Default, Clone, Copy)]
pub struct Child;

impl Child {
  pub fn get(tree: &UiTree, parent: NodeId) -> Option<NodeId>;
  /// Replaces the child: checks `child`'s links in both trees, then detaches the old child and
  /// links `child`. When a check fails, nothing changes and the old child stays.
  pub fn set(tree: &mut UiTree, parent: NodeId, child: Option<NodeId>);
}
```

`Children` and `Child` are for content whose logical and visual parent are the same element, as a panel's and a `Border`'s are. A templated control (#84) is different: its content is a logical child of the control and a visual child of a template part, which #84 links itself. So the "same parent in both trees" rule lives with `Children` and `Child`, not in `UiTree`.

The two trees can disagree, since a template gives a node different logical and visual parents, so a change to both is checked in both before either is made: otherwise the second link could fail after the first succeeded and leave the trees out of step. `UiTree` exposes the checks its link methods already make, as `check_link(tree_kind, parent, index, child) -> Result<(), LinkError>` (a node not in the tree, an index past the end, a cycle), and `Children` runs it for both trees first. `remove` takes the parent and checks that `child` is its child in both trees, so it can't detach a node from another panel.

`Children::add`, `insert` and `remove` panic when a check fails, as the `UiTree` methods do: in code, those are bugs. The loader reaches them through `XamlCollection`, which returns the failed check as an error instead, since markup is input.

`XamlCollection` changes so one trait serves both a collection that lives in the tree and one that lives in its field. The derive generates `add_child` for the content field, passing an accessor from the owner node to that field:

```rust
pub trait XamlCollection: Sized {
  /// Adds `child` as content of `owner`. `field` reaches this collection inside the owner.
  fn push_child(
    tree: &mut UiTree,
    owner: NodeId,
    child: NodeId,
    field: for<'a> fn(&'a mut UiTree, NodeId) -> Option<&'a mut Self>,
  ) -> Result<(), ValueError>;
}

// generated for StackPanel's content field:
//   |tree, owner, child| Children::push_child(tree, owner, child,
//     |tree, owner| tree.get_as_mut::<StackPanel>(owner).map(|panel| &mut panel.children))
```

Every implementation calls `field` first, and refuses with `ValueError::WrongType` an owner it doesn't reach, a node of another type, before changing anything. `Children` then links `child` into both trees, returning `ValueError::InvalidChild` (new), with the `LinkError`, when a check fails. `Child` does the same, and also refuses a child when the owner has one already, since markup gives a single-child element one child. A value collection such as `LinearGradientBrush`'s `Vec<GradientStop>` ([value objects](value-objects.md)) takes the staged value out of the tree, as `from_object` does, and pushes it through `field`. The `Vec<NodeId>` implementation is removed; nothing calls `push_child` yet.

The builder ([builder API](builder-api.md), #43) takes children in the same expression as the properties, before `build` has the tree. The ids wait in a wrapper, not in the node, since a relationship is tree data:

```rust
let ok = Button::new().content("Hi").build(tree);
let panel = StackPanel::new()
  .spacing(8.0)
  .children([ok])   // WithChildren<StackPanel, [Handle<Button>; 1]>
  .build(tree);     // builds the node, then links each child

/// A node waiting to be built, with the children to link once it is.
pub struct WithChildren<T, I> {
  node: T,
  children: I,
}

impl<T: XamlType + Object, I: IntoIterator<Item: Into<NodeId>>> WithChildren<T, I> {
  pub fn build(self, tree: &mut UiTree) -> Handle<T>;
}
```

`build` checks that every item is in the tree before it allocates the node, and panics if one isn't: in code that is a bug, as for `Children::add`. Once those checks pass no link can fail, because a node that was just allocated has no ancestors to make a cycle and no children to collide with, so a failed build never leaves a parent or some of its children in the tree.

The derive generates `.children(items)` for a `Children` field and `.child(item)` for a `Child` field, which wraps `Some(item)` in the same `WithChildren`; a leaf gets neither. `WithChildren::build` adds each item through the type's content field, the path markup takes, so a second child for a `Child` field is refused the same way in both. `WithChildren` has no property methods, so `.children` comes last before `.build`, as children come after attributes in markup. It is one generic type, unlike the per-type builder types `builder-api.md` rejects, and that document's "`build` links its children" becomes "`WithChildren::build` links them". The builder methods don't exist yet, so `WithChildren` and the generated `.children` come with #43; this design fixes their shape.

## 5. `Panel` and `StackPanel`

`Panel` is the property group every panel flattens, in `artic-controls`:

```rust
/// What every panel has: a background drawn under its children.
#[derive(Debug, XamlProperties)]
pub struct Panel {
  #[xaml(affects = render)]
  pub background: Property<Option<Brush>>,
}

impl Panel {
  /// Fills the element's bounds with `Background`, if it's set.
  pub fn render(&self, cx: &RenderCx<'_>, scene: &mut SceneBuilder);
}
```

Every panel's `Background` is the same property with one key, so a style that sets `Background` works on any panel. Each panel declares its own `#[xaml(content)] children: Children`, so a type's XAML content is visible where the type is. There is no `<Panel>` element.

`StackPanel` has `Orientation`, `Vertical` by default, and `Spacing`, 0 by default. Below, the stacking axis is height when `Vertical` and width when `Horizontal`, and the cross axis is the other.

| Step | Rule |
| --- | --- |
| Measure | each child is offered the panel's available cross size and infinity on the stacking axis. The desired stacking size is the children's sum plus `Spacing` between each pair; the desired cross size is the largest child's. No children gives 0×0 |
| Arrange | children are placed from the start of the stacking axis with `Spacing` between them. Each slot is as long as the child asked for on the stacking axis and as wide as the panel on the cross axis; the child's own margin and alignment place it inside. Space left over stays empty, and children past the end are still arranged |
| `Spacing` | a value that isn't a finite number of 0 or more counts as 0, so children don't overlap by accident |
| Overflow | sums and positions along the stacking axis use the saturating operations of section 3, so a huge `Spacing` or huge children can't add up to infinity |
| Render | `self.panel.render(cx, scene)` |
| Accessibility | nothing added: the default role is `GenericContainer` |

Measure and arrange are each written once, over a private `Axis` helper that splits a size into its stacking and cross parts and joins them back.

## 6. Accessibility

Elements return their own node; the tree of nodes is built by #54's walk, which takes children from the visual tree in order and skips nodes layout didn't place. Child order is that walk's job for every element, so `StackPanel` only checks its role here, and #54's `stack_panel_children_in_visual_order` checks its children's order, with collapsed children left out.
